## PART 2. 요구사항

### 2-1. 사용자 역할

회원가입할 때 두 역할 중 하나를 고릅니다.

| 역할 | 누구 | 할 수 있는 것 |
| --- | --- | --- |
| `CUSTOMER` | 손님 | 메뉴 조회 · 주문 생성 · 주문 취소 · 결제 · 내 주문 조회 |
| `OWNER` | 사장님 | 메뉴 등록·수정·삭제 · 내 메뉴에 들어온 주문 조회 · 주문 상태 변경 |

### 2-2. 꼭 저장해야 하는 정보와 연관관계

아래는 **꼭 들어가야 하는 정보**입니다. 필드 이름, 타입, 테이블 구조는 여러분이 직접 설계합니다. 필요하다고 생각하는 필드는 자유롭게 추가해도 됩니다.

| 대상 | 꼭 저장해야 하는 정보 | 누구와 연결되나요? |
| --- | --- | --- |
| 회원 | 아이디(중복 불가) · 비밀번호(BCrypt 암호화 · 단방향 해시) · 역할 | — |
| 메뉴 | 이름 · 가격 · 설명 · 삭제 여부(Soft Delete) | 어느 **사장님**의 메뉴인지 |
| 주문 | 수량 · 총액 · 배송 주소 · 주문 상태 | **누가** 주문했는지, **어떤 메뉴**인지 |
| 결제 | 결제 금액 · 결제 수단(카드) · 결제 상태 | **어떤 주문**의 결제인지 |

그리고 **모든 테이블**에 **생성 시각과 수정 시각**이 자동으로 기록되어야 합니다.

<aside>
🔗

**필수 연관관계 4개 — 전부 N:1**

- 메뉴 → 사장님(회원): 사장님 한 명이 메뉴를 여러 개 가집니다.
- 주문 → 주문자(회원): 손님 한 명이 주문을 여러 번 합니다.
- 주문 → 메뉴: 메뉴 하나에 주문이 여러 건 들어옵니다.
- 결제 → 주문: 한 주문에 결제 기록이 여러 개 쌓일 수 있는 구조로 둡니다(예: 결제 취소 후 다시 결제). 단, **"결제 완료"는 한 번만** 가능합니다.

네 관계 모두 `@ManyToOne`으로 매핑하고, **지연 로딩**(`FetchType.LAZY`)을 적용합니다. 참고로 `@ManyToOne`은 기본값이 즉시 로딩(`EAGER`)이라, 지연 로딩은 직접 지정해야 합니다.

</aside>

### 2-3. 주문 상태 흐름

주문은 아래 순서로만 상태가 바뀝니다. 상태 이름은 예시이고, enum 이름은 자유롭게 정해도 됩니다.

```
[주문요청 ORDERED] ──(손님이 결제)──▶ [결제완료 PAID] ──(사장님이 수락)──▶ [주문수락 ACCEPTED] ──(사장님이 완료)──▶ [배달완료 COMPLETED]
        │
        └──(손님이 취소 · 결제 전에만)──▶ [주문취소 CANCELED]
```

| 누가 | 할 수 있는 상태 변경 |
| --- | --- |
| 손님 (`CUSTOMER`) | 주문요청 → 결제완료 (결제 기능으로) · 주문요청 → 주문취소 |
| 사장님 (`OWNER`) | 결제완료 → 주문수락 · 주문수락 → 배달완료 |

표에 없는 변경은 **막아야 합니다.** 예를 들어 주문요청에서 바로 배달완료로 가거나, 결제가 끝난 주문을 취소하는 건 안 됩니다.

<aside>
📌

**체크리스트 읽는 법**

- ☐ 하나가 **구현하고 확인해야 할 조건 하나**입니다.

- "이미 결제된 주문을 또 결제"처럼 **규칙에 어긋나는 요청**은 400이나 409 중 하나로 정해서 **일관되게** 쓰면 됩니다.
</aside>

#### 👤 회원

**1. 회원가입** · 누구나

- [ ]  아이디 · 비밀번호 · 역할(`CUSTOMER` 또는 `OWNER`)을 받아 가입합니다. 성공하면 **201**.
- [ ]  아이디는 **4~20자**, 비밀번호는 **8자 이상**입니다. 비어 있거나 조건에 맞지 않으면 **400**.
- [ ]  이미 있는 아이디로는 가입할 수 없습니다(**409**).
- [ ]  비밀번호는 BCrypt로 암호화(단방향 해시)해서 저장하고, **응답에는 비밀번호를 담지 않습니다.**

**2. 로그인** · 누구나

- [ ]  아이디·비밀번호가 맞으면 **JWT를 발급**합니다. 응답 본문이나 헤더 중 편한 곳에 담아 돌려줍니다(**200**).
- [v]  토큰에는 아이디와 역할, **만료 시간**을 담습니다. 비밀번호 같은 민감정보는 담지 않습니다.
- [ ]  아이디가 없거나 비밀번호가 틀리면 **401**.
- [v]  로그인이 필요한 요청은 `Authorization: Bearer {토큰}` 헤더로 보내고, 서버는 요청마다 필터에서 토큰을 검증합니다.

#### 🍜 메뉴

**3. 메뉴 등록** · OWNER

- [ ]  이름 · 가격 · 설명(선택)을 받아 등록합니다. 성공하면 **201**.
- [ ]  이름이 비어 있거나 가격이 1원보다 작으면 **400**.
- [ ]  메뉴의 주인은 **요청한 사장님**입니다. 요청 본문이 아니라 토큰에서 누구인지 꺼냅니다.
- [ ]  CUSTOMER가 요청하면 **403**.

**4. 메뉴 목록 조회** · 누구나

- [ ]  로그인하지 않아도 메뉴 목록을 볼 수 있습니다(**200**). **삭제된 메뉴는 빼고** 보여줍니다. 페이징은 도전 기능입니다.

**5. 메뉴 단건 조회** · 누구나

- [ ]  메뉴 하나의 정보를 봅니다(**200**). 없거나 삭제된 메뉴면 **404**.

**6. 메뉴 수정** · OWNER

- [ ]  이름 · 가격 · 설명을 수정합니다(**200**). 값 검증은 등록과 같습니다(**400**).
- [ ]  **본인 메뉴만** 수정할 수 있습니다. 다른 사장님의 메뉴면 **403**, 없거나 삭제된 메뉴면 **404**.
- [ ]  수정하면 수정 시각이 자동으로 바뀝니다(JPA Auditing).

**7. 메뉴 삭제 (Soft Delete)** · OWNER

- [ ]  DB에서 실제로 지우지 않고 **"삭제됨"으로 표시**만 합니다(예: 삭제 여부나 삭제 시각 컬럼). 성공하면 **200 또는 204**.
- [ ]  **본인 메뉴만** 삭제할 수 있습니다. 다른 사장님의 메뉴면 **403**, 없거나 이미 삭제된 메뉴면 **404**.
- [ ]  삭제된 메뉴는 **목록에서 빠지고**, 단건 조회 · 수정 · 주문에서는 **없는 메뉴처럼(404)** 처리합니다.
- [ ]  삭제된 메뉴로 이미 들어온 **주문 기록은 그대로** 남아 있어야 합니다.

<aside>
💡

**왜 실제로 지우지 않나요?**

주문은 메뉴를 외래키로 가리키고 있습니다. 주문이 들어온 메뉴를 `DELETE`로 지우려고 하면 PostgreSQL이 `violates foreign key constraint` 에러로 거절합니다. 억지로 지우게 만들면 이번엔 주문 기록이 가리키던 메뉴가 사라져서 "이 주문은 뭘 시킨 거지?"가 됩니다. 그래서 주문·결제처럼 **기록이 중요한 데이터가 걸려 있으면, 지우지 않고 "삭제됨" 표시만** 합니다.

참고로 실무에서는 주문 당시의 메뉴 이름·가격을 주문 쪽에 복사해 두는 **스냅샷**도 함께 많이 씁니다. 메뉴 이름이나 가격이 나중에 바뀌어도 주문 내역은 주문 당시 그대로 보여야 하기 때문입니다. 이번 과제의 총액도 주문할 때 계산해서 저장하니, 메뉴 가격이 바뀌어도 그 주문의 총액은 그대로 남습니다. 다만 주문이 메뉴를 외래키로 가리키는 설계라면 메뉴 행을 실제로 지울 때 위 에러가 나므로, 스냅샷을 두더라도 Soft Delete가 함께 필요합니다.

</aside>

#### 🧾 주문

**8. 주문 생성** · CUSTOMER

- [ ]  메뉴 ID · 수량 · 배송 주소를 받아 주문합니다. 성공하면 **201**.
- [ ]  수량은 **1 이상**, 배송 주소는 **필수**입니다. 어기면 **400**. 없거나 삭제된 메뉴면 **404**.
- [ ]  **총액 = 메뉴 가격 × 수량**을 서버가 계산해서 저장합니다. 요청으로 금액을 받지 않습니다.
- [ ]  주문자는 토큰에서 꺼내고, 처음 상태는 **주문요청**입니다.
- [ ]  OWNER가 요청하면 **403**.

**9. 주문 목록 조회** · 로그인한 사용자

- [ ]  CUSTOMER가 부르면 **본인이 한 주문만** 나옵니다.
- [ ]  OWNER가 부르면 **본인 메뉴에 들어온 주문만** 나옵니다.
- [ ]  조회는 Spring Data JPA **Query Methods**로 만듭니다.

**10. 주문 취소** · CUSTOMER

- [ ]  **본인 주문만** 취소할 수 있습니다. 다른 손님의 주문이면 **403**.
- [ ]  **주문요청 상태일 때만** 취소됩니다. 결제가 끝난 주문 등은 거절합니다(**400 또는 409**).
- [ ]  취소되면 상태가 **주문취소**로 바뀝니다(**200 또는 204**).

**11. 주문 상태 변경** · OWNER

- [ ]  **본인 메뉴에 들어온 주문만** 바꿀 수 있습니다. 아니면 **403**.
- [ ]  **결제완료 → 주문수락**, **주문수락 → 배달완료** 두 가지만 허용합니다(**200 또는 204**).
- [ ]  그 외 변경(예: 결제 전 주문을 수락, 배달완료된 주문을 다시 변경)은 거절합니다(**400 또는 409**).

#### 💳 결제

**12. 결제** · CUSTOMER

- [ ]  **본인 주문만** 결제할 수 있습니다. 아니면 **403**.
- [ ]  결제 수단은 **카드만** 받습니다(그 외 값은 **400**).
- [ ]  결제 금액은 요청으로 받지 않고, **주문 총액을 서버가 그대로** 씁니다.
- [ ]  **주문요청 상태일 때만** 결제됩니다. 이미 결제됐거나 취소된 주문은 거절합니다(**400 또는 409**).
- [ ]  성공하면 결제 내역을 저장하고, 주문 상태를 **결제완료**로 바꿉니다(**201**).

<aside>
💡

**금액은 왜 서버가 계산하나요?**

요청 본문에 `"totalPrice": 100`을 보내는 건 누구나 할 수 있습니다. 클라이언트가 보낸 금액을 그대로 저장하면, 만 원짜리 주문을 백 원에 결제할 수 있게 됩니다. 그래서 **총액과 결제 금액은 항상 DB에 있는 메뉴 가격으로 서버가 계산**합니다.

</aside>

### 2-5. 공통 요구사항

- [ ]  **3 Layer**: Controller(요청·응답) – Service(비즈니스 로직) – Repository(DB 접근)로 역할을 나눕니다.
- [ ]  **DTO 분리**: 요청·응답은 DTO로 주고받고, Entity를 그대로 응답하지 않습니다. 회원 Entity를 그대로 응답하면 비밀번호까지 나갈 수 있습니다.
- [v]  **Entity 설계**: 기본키 생성 전략(예: `GenerationType.IDENTITY`)을 정하고, 꼭 있어야 하는 값은 `@Column(nullable = false)`, 아이디처럼 겹치면 안 되는 값은 `unique = true`로 **DB에도** 제약을 겁니다. 서비스에서 중복을 검사해도, 거의 동시에 들어온 가입 요청 두 건은 둘 다 검사를 통과할 수 있기 때문입니다. 엔티티를 처음 만들 때 같이 걸어두세요.
- [v]  **연관관계**: 2-2의 4개 관계를 `@ManyToOne` + 지연 로딩으로 매핑합니다.
- [v]  **JPA Auditing**: 공통 부모 클래스(BaseEntity)로 생성·수정 시각을 자동 기록합니다.
- [ ]  **Query Methods**: 아이디 중복 확인, 역할별 주문 목록 조회 등을 메서드 이름 규칙으로 만들어봅니다.
- [ ]  **Validation**: 요청 DTO에 검증을 걸고, 실패하면 **400**으로 응답합니다.
- [v]  **Spring Security + JWT**: 로그인하면 토큰을 발급하고, 요청마다 필터에서 토큰을 검증하고, 역할에 따라 접근을 제한합니다.
- [ ]  **RESTful URL**: 자원은 URL(명사)로, 행위는 HTTP 메서드로 표현합니다(4-3의 규칙 참고).
- [ ]  **상태 코드**: 생성 201, 잘못된 요청 400, 권한 없음 403, 없는 대상 404처럼 **상황에 맞게** 응답합니다.
- [v]  **비밀번호**는 절대 평문으로 저장하지 않습니다(BCrypt).
- [v]  **enum**(역할·주문 상태 등)은 **문자열**(`EnumType.STRING`)로 저장합니다. 숫자(ORDINAL)로 저장하면 enum 순서가 바뀌는 순간 기존 데이터의 의미가 달라집니다.

🧭

**구현 순서 힌트** — 설계 → 엔티티 → 회원·인증 → 메뉴 → 주문·결제
인증을 먼저 붙여두면, 주문을 만들 때 **"누가 주문했는지"를 토큰에서 바로 꺼내 쓸 수 있어서** 코드를 두 번 고치지 않아도 됩니다.
